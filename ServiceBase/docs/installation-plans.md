# 安装计划与多步骤队列（第 7、8 步）

2026-09-22。本文记录第 7、8 步（v7）；后续 v8 已扩展卸载和更新，见 [第 9 步](package-maintenance.md)。服务端、网页与独立 Unity 执行器已实现；验证环境 Unity 2022.3.62f2。统一阶段编号见 [开发顺序](development-order.md)。

## 使用流程

1. 选择已连接 v7 执行器的工程，在包详情选发布 Tag，点击“预览安装”。已安装 commit 可查看信息；再次预览需选目录中的发布 Tag。
2. 弹窗列出依赖顺序中的新增、变更、已满足包。展开每个包，选择附带插件；选中 ZIP 时通过网页浏览工程 Assets 并选择根目录。
3. 点击“检查冲突和执行顺序”。同插件不同版本/目录、同目标文件、不同路径重复 GUID 会提示，仍允许确认；取消勾选或修改 ZIP 目录后必须重新检查。
4. 确认生成持久任务。依赖先于根包，所选插件先于所属包；相同构建和相同目录只执行一次，其余重复项/未选项显示跳过。
5. 原任务区域以横向卡片显示最近 10 条记录：成功绿、失败红、取消灰、进行中橙；点击卡片打开详情。总进度按已完成及已跳过步骤计算，执行中的单步使用不定量动态进度条；已完成/跳过步骤灰显，可定位当前步骤。页面关闭重开后从服务读取任务。
6. 最后一条由 Unity 核对全部目标包、保留的工程依赖、manifest、lock、注册信息、插件逐文件状态和编译状态，再报告整队完成。

## 代码分工与接口

- `ProjectPackageState.cs`：独立读取已注册包、完整标准/Git 依赖、内置包目录、Registry 配置；原始 manifest/lock 留在工程。每 10 秒空闲采样，和插件状态分次上传以满足请求大小限制。
- `package_state.py` / `ProjectPackageState`：接受同会话、受限大小的快照；拒绝使用超过 120 秒的基线，忽略延迟到达的旧快照。
- `plan_resolver.py`：读取真实 package.json，解析 `dependencies`、`dependenciesGit` 与工程其他根包约束，固定 Git commit，迭代重算版本约束并拓扑排序。读取所选 commit 的精确插件映射并核验元数据指纹。
- `installation_plans.py` / `InstallationPlan`：持久化预览、摘要及最终选择；准备不可变插件制品；确认时在工程锁内复查会话、工程指纹、预览时效及执行器能力。
- `InstallJob → InstallStep → InstallAttempt`：Job 多步骤串行，Step 多次人工尝试。旧 Job 保持单步兼容。步骤目标保存在 Step，旧行为空时兼容读取 Job 目标。
- `installations.py`：幂等回执、当前步骤派发、项目锁、暂停/取消后续步骤、明确失败的人工重试、最终完成判定。
- `installation-plan.mjs`：预览、复选框、网页 ZIP 目录、冲突与顺序确认。`installations.js` 展示整个任务。
- 已移除网页直接填写 UPM 包名和固定标识的调试表单；安装入口统一使用包/插件详情。原单操作接口仍供插件操作和执行协议使用。
- `DELETE /api/projects/<project>/installations/<job>/` 从历史列表删除已结束记录；运行、暂停、等待核对和正在取消的任务拒绝删除。`InstallJob.history_deleted_at` 仅影响历史列表，不删除安装计划、步骤和回执，保留 Tag、依赖归属、清理判定和重复回执确认。重复删除幂等；已删除任务拒绝从旧页面重试。部署需迁移 0014，无需更新 Unity。

新增接口（均经过工程权限校验及网页 CSRF 校验）：

- `GET/POST /api/projects/<project>/installation-plans/`：最近预览 / 创建预览。
- `POST /api/projects/<project>/installation-plans/<plan>/selection/`：检查选择、制品与冲突，返回执行顺序及选择摘要。
- `POST /api/projects/<project>/installation-plans/<plan>/confirm/`：确认固定计划；重复确认相同选择返回同一 Job。
- `POST /api/projects/<project>/installations/<job>/control/`：`pause`、`resume`、`cancel`。
- 既有 jobs/sync/receipt 接口兼容单步与多步，v7 才能首次领取计划步骤。

## 中断和恢复

- **域重载或编辑器重启**：沿用每个 Attempt 的持久日志、意图标记、工程归属记录及回执。已开始的修改只核对，不重复 Add/导入。
- **完成确认丢失**：服务接受完成回执时不同时派发下一条。Unity 确认并归档上一条，再发无回执请求，服务才允许派发下一条。
- **服务重启/页面关闭**：计划、选择、步骤、尝试、最后指纹、暂停/取消状态全部存在数据库；缓存只是在线能力与心跳，不决定完成。
- **暂停**：停止后续派发，已派发步骤继续完成或核对。保留工程锁。
- **取消**：跳过未派发步骤。已派发步骤必须取得确定结果；未知状态继续占锁。已完成步骤保留，不回滚。
- **失败**：保留整个计划的工程锁。只有确定未开始或 Add 已明确返回失败，才允许记录原因并重试当前步骤。不会重跑前面成功步骤。
- **超时/断线**：超过 10 分钟无步骤进度显示需要核对；失联显示等待连接。两者都不等于失败，也不会自动重装或释放锁。
- **工程被外部修改**：每步开始前检查 manifest/lock 指纹；每步成功保存新指纹。最终再次检查全图与原有配置。偏离预览则停在失败/需要核对，保留结果。
- **解析被中断**：无安装副作用。解析有 80 秒工作预算、单次远端请求 12 秒超时、100 个包/64 层/500 步上限。超过两分钟未完成的预览在读取时标为中断；重新生成。确认只接受一小时内的预览。

## 范围与约束

- 工程包列表、依赖树和安装预览只展示 MT Git 包（工程中的 MT 本地包保留识别提示）。Unity 内置包及 Registry 包仍保留在完整状态、安装执行顺序和最终校验中，不改变底层依赖保护。
- 配置 GitLab 上同仓库、同子目录的 Git 依赖按 `package.json.version` 比较：从本次依赖要求、其他根包约束和已安装依赖中选择较高版本，按 MT 向下兼容处理；不主动选仓库最新版本。重新展开选中版本的依赖与精确插件映射，预览提示自动统一的版本。明确选择的根包允许降级，但仍需满足其他根包约束。
- 不同仓库的同名包、最高版本相同但 commit 不同仍需人工处理，不能用 SHA 大小或任意先后顺序判断版本；Unity 版本要求和精确插件映射校验继续有效。

### 其他约束
- Git 只从已配置的 GitLab 读取元数据，Tag 转为完整 commit，支持包子目录。依赖元数据兼容 HTTPS、`ssh://git@主机/仓库.git#Tag` 和 `git@主机:仓库.git#Tag`；SSH 必须与该 GitLab 公布的仓库地址、端口一致。解析后统一下发无凭据的 HTTPS + 完整 commit。Unity 机器仍需具备自己的 Git 访问凭据；服务凭据不进入下发链接。
- Registry 默认只允许 `https://packages.unity.com`。额外项目 scoped Registry 必须在服务 `SERVICEBASE_ALLOWED_REGISTRIES` 中明确配置，当前元数据获取不支持私有 Registry 的额外认证配置。
- 不猜测缺失插件映射，不借用其他版本；本地/嵌入包不能作为覆盖目标。服务只接管本次执行记录。
- 对新增/变更依赖逐条 Add 会使其成为 manifest 直接依赖。计划保存原有根包和新图，供第 9 步卸载时计算引用；当前不会自动改回间接依赖。
- 页面中的根包/依赖包使用服务安装记录与实际包依赖图计算，不直接采用 Unity 的 `isDirectDependency`。用户单独选择的包及原有直接依赖作为根（depth=0）；服务随计划添加的依赖按距所有根的最短路径显示 depth，共享依赖在每个父节点下保留。取消计划后残留、暂不可达的已安装依赖保留依赖身份，并作为断开的组件展示。
- 安装计划另外保存解析前的 `requested_ref` 和根包目录标识。展示时仅将已成功安装且仍匹配当前包身份的记录用于还原 Tag；旧记录可通过插件索引中精确的包名、commit、GitLab 工程与 Tag 映射恢复。无法唯一确认时保留 commit，不凭版本号猜测 Tag。列表与工程依赖树使用同一份标签和深度；执行链接、Unity manifest/lock、实际 commit 校验保持固定 SHA。
- 预览允许提交文件冲突，实际导入保留原有文件保护：不同内容不会静默覆盖，相关步骤会停止。复杂的插件升级/覆盖合并属于第 9 步。
- 若插件和所属包必须同时出现才能编译，v10 会记录插件编译失败并跳过此插件步骤，继续执行后续包安装；最后仍严格核对包图。详见 [v10 执行规则](plugin-execution-v10.md)。
- 依赖解析使用明确三段版本（含预发布），不接受 latest、版本范围等模糊输入。最终以实际 UPM 结果再次核验。
- 新安装代码不引用 MTP 类型、业务或本地安装记录。v7 的网页工程快照刷新也不排入 MTP 任务；原有 MTP 工程的后台 Bridge 行为属于已有系统。已识别 MTP 的工程仍受 `MtpBoundary` 阻止新修改，严格共存与迁移尚未完成。
