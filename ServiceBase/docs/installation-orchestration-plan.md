# 服务端编排 UPM 与插件安装：讨论稿

日期：2026-09-15。状态：待讨论；本文件不代表已实现或已完成实机可靠性验证。

本轮范围更新：已建立离线插件仓库及工程包映射，见 ../external/README.md；已完成统一只读查询接口和工作台插件仓库标签页，接口与权限见 development.md。第三步独立 Unity 执行器与单包 UPM 闭环的实现及验证范围见 single-upm-installation.md；单条 unitypackage/ZIP 导入已实现，ZIP 由网页预选目录、Unity 自动执行，见 plugin-imports.md；第 7、8 步完整依赖编排已实现，当前实现和验收以 [安装计划](installation-plans.md) 为准。具体共存限制及候选记录迁移见 mtp-separation.md。

## 1. 结论与边界

采用服务端生成不可变执行计划、Unity 单步骤执行、两端持久化并核对实际结果的架构。可实现断线、服务重启、脚本域重载后的可恢复安装；不承诺任意插件都能无人值守安装，也不承诺全流程事务回滚。

可靠性的定义：不误报成功；不因重发而盲目重复导入；中断后可识别进度；不能确定时停止后续修改并提供恢复入口。Unity 卡死、启动时编译失败导致 Bridge 未加载、插件自定义导入副作用等情况可能需要用户处理。

当前基础：ServiceBase Bridge 仅支持消息 mock 与快照；服务任务固定 60 秒过期。现有目录是展示模型，dependenciesGit 被简化为名称与 tag；不是执行级依赖求解器。MTP 已有安装恢复与 unitypackage 路径解析，可参考机制，但新的执行器独立实现、不依赖 MTP 初始化。

## 2. 整体流程

1. 获取目标工程最新快照、Unity/Bridge 版本、忙闲与编译状态。
2. 读取指定版本的完整包元数据及插件映射；合并 dependenciesGit、标准 UPM dependencies、已安装包约束。
3. 解析依赖冲突、共享依赖与循环；检查 Unity 兼容性、仓库可达性、插件制品和文件冲突。
4. 安装前弹窗列表展示依赖树的新增/变更包；每个包可展开附带插件，用户逐项复选导入，并在网页预选 ZIP 根目录。同文件插件（含不同版本）的勾选冲突提供警告，不禁止确认安装。包顺序使用依赖先于根的拓扑排序。
5. 固定执行计划及摘要：包名、源、tag、解析后的 commit、包子目录、插件 ID/版本/构建号/内容哈希、映射版本、工程基线。之后重试不重新选择 latest。
6. 服务为同一工程仅授权一个修改步骤；Unity 将步骤先落盘，再执行单次 UPM Add、单次插件导入或单次插件删除。
7. Unity 记录回调与实际结果；无需强制重载，没有重载时也正常核验；发生重载后从日志进入核验。
8. Unity 将结果写入本地待回执队列并持续重发，服务幂等接受并提交步骤结果，再开放下一步。
9. 确认后网页展示固定安装/导入列表，按依赖顺序排列包，在每个包之前插入其选中的插件步骤，全程自动串行执行。每项呈现待安装、安装中（转圈）、已安装及异常状态。最终核对全部目标包及插件状态，防止后续 UPM Resolve 改变此前结果。

包仓库服务器可访问不等于 Unity 可访问。Git URL 方式需要 Unity 机器具备网络与 Git 认证；服务器凭据不嵌入 URL 下发。若改为服务器镜像/制品代理，应作为另一项交付明确实现与测试。

标准 UPM 依赖可能由 Client.Add 自动解析，单次 Add 不等于只改变一个包。显式逐条添加还会把部分间接依赖变成 manifest 的直接依赖；计划要记录原始根、服务添加项及最终图，避免未来卸载误删共享依赖。

## 3. 必需插件与编译顺序

2026-09-20 更新：所有插件选项在安装前的网页预览中确认。每个包附带的已选插件安排在该包安装之前，不在执行到一半时再询问。

映射保留插件关联和排序约束，计划记录用户的选择与 ZIP 目录。多个包引用完全相同的插件构建及目标目录时可复用结果，在首次需要它的包之前执行；不同版本不静默去重。同文件勾选冲突仅警告，允许用户继续安装。此项是未来预览交互要求，不表示当前导入器会无提示覆盖已有不同内容文件；后续实现需明确实际覆盖和编译失败的处置，不能因预览允许继续就丢弃文件保护。

如果包与插件必须共同存在才能编译，且找不到安全单步顺序，首版判为不支持的组合；先调整打包/程序集结构，不靠长时间锁域重载解决。Bridge 使用不引用 MTP/业务程序集的 Editor 程序集，必要时评估预编译实现，但仍需实测编译错误和重启，不把程序集隔离当成绝对保证。

## 4. 插件仓库与元数据

建议开发期放在 ServiceBase/external/magictavern/<plugin-id>/<version>/<build-id>/。magictavern 表示内部维护渠道，不表示原作者。根目录可配置，部署时挂持久卷；大文件不进入普通源码 Git，数据库与文件一起备份。

每个发布构建包含：

- plugin.json：仅用户要求的 name、format（zip/unitypackage）、version、published_at、unity、description。
- artifact.zip 或 artifact.unitypackage：不可覆盖的发布制品；相同上游版本内部重打包用不同 build-id。
- manifest.json：工具生成的技术索引，包括 schema_version、稳定 plugin_id、build_id、制品 SHA-256/大小、文件列表、GUID/.meta 信息、预期路径与安装布局。暂不把技术字段塞入展示 JSON。

Unity 要求首期可用字符串展示；执行时只自动判断支持的明确范围，无法解析不当作兼容。上架流程先临时写文件、解析并校验、生成索引，完成后一次发布；缺制品或缺索引的条目不供安装。执行期间引用的历史制品禁止覆盖或回收。

包到插件映射首期采用可版本化 JSON 为唯一编辑来源，DB 保存导入索引及执行快照。按包完整名称 + 精确发布版本/commit 映射至 plugin_id/version/build_id；关联项含 required、phase、order 及安装布局覆盖。不要只按包名或 zip 文件名匹配。未来打包器输出同一 schema；后台可写映射时再明确切换 DB 为唯一来源，避免双向编辑。

现有包从各自指定 revision 的 Editor/PluginsPackage 枚举迁移，制品复制到 magictavern；按哈希去重但保留来源与引用。先生成映射报告供核对，再上架。旧包里留存的压缩文件暂不改；确保服务安装路径不触发 MTP 再次自动导入。

ZIP 布局需明确：当前由网页为每次导入选择现存 Assets 内根目录，保持 ZIP 原有结构，不自动 strip 顶层目录。所选目录固定到计划和尝试记录。需要写 Packages 缓存的旧布局首版列为迁移项，避免把易被 UPM 重建的缓存当作持久安装位置。

## 5. 服务端持久化与执行协议

使用现有数据库扩展，不把 HTTP 请求、浏览器连接或进程内队列作为任务存活条件。首期可通过短轮询驱动、事务提交状态；不必先引入复杂队列。守护扫描负责超时提示与恢复标记，不直接重新执行 Unity 操作。

建议实体：

- InstallJob：目标工程、不可变计划/摘要、工程基线、整体状态、当前步与状态版本。
- InstallStep：固定 step_id、动作、制品、依赖、用户决策、执行结果与验收证据。
- StepAttempt：attempt_id、执行器世代号、运行会话、领取/启动时间、最近存活、最近进展、阶段与错误。
- StepEvent：去重事件 ID、阶段序号、时间、脱敏诊断；旧/乱序事件不得倒退终态。
- ProjectPluginInstallation：每工程插件安装记录、制品标识、实际文件清单、共享引用及本地修改状态。

步骤阶段：queued → offered → accepted → running → verifying → succeeded。waiting_user、waiting_editor、reconciling 为可恢复等待；failed、cancelled、skipped 明确区分。重载/编译可作为 running/verifying 的阶段信息。

服务先事务记录授权，再返回给 Unity。Unity 先持久化接收和启动意图，再调用修改 API。重复收到同一步：已完成就重发结果，执行中只报告状态，状态不明就核验，不再调用导入。

每工程服务事务约束 + Unity 本地锁保证服务自身单执行者。租约/存活期限用于发现失联，不能当作旧操作已停止的证明。新会话或新 attempt 获得修改权前，先核对旧日志与实际工程状态；无法证实旧执行终止则等待。世代号用于拒绝旧授权和旧事件覆盖新状态，但不能撤销已进入 Unity API 的操作。

旧 attempt 的迟到成功证据保存并进入核对，不能悄悄丢弃，也不能直接覆盖较新步骤。Job 挂稳定工程身份，session 仅代表当前编辑器运行；重启采用显式恢复握手，校验工程身份、本地计划摘要与服务记录。服务器无历史记录、本地日志丢失、工程复制或移动时不猜测续跑。

用户手动通过 MTP/Package Manager 修改不能被服务锁完全禁止。执行前核对包清单指纹、忙闲及步骤前置条件；发现偏移停止重新规划。运行期避免并用两个安装器；服务修改根和状态追踪不依赖旧 MTP 私有缓存，旧 UI 记录不同步需明确展示或另做适配。

## 6. Unity 单步骤执行器与结果验证

Unity 工程根 .servicebase/ 保存原子写入的操作日志、回执、插件文件归属与必要备份；不放 Assets、不只用 SessionState，也不依赖可清理的 Library 保存唯一恢复数据。下载缓存可放 Library。运行日志加入忽略规则，明确工程复制时的身份处理。

持久化点：接收步骤、修改前计划/文件基线、API 启动意图、收到回调、验证结果、待发送回执。用临时文件 + 原子替换保留可恢复版本；磁盘不足/日志写失败时不开始修改。

UPM：记录目标源、commit/版本，使用单次 Client.Add；核验注册包、manifest/lock 与 resolved path 元数据，不仅查目录或 name/version。Git 内部重打包同版本需确认实际 commit。正在进行的 UPM 操作结束后才发起 Client.List 等下一次 Client 调用。没有原请求对象时先等待编辑器可核验；无法确认不盲目重发。

unitypackage：开始前解析预期路径、GUID 与内容清单；注册 started/completed/failed/cancelled 回调并尽快持久化。回调不是可跨重载的队列，重载后以日志和文件/GUID 状态补充核验。仅有根目录存在或“已调用 ImportPackage”不足以成功。

区分“制品内容已应用”与“编辑器已完成处理/可继续”。没有回调但预期内容完整可记录恢复验证结果，不伪造回调；自定义导入器会修改资源、生成额外文件或触发外部副作用时，需专用验收规则，否则进入待核对。编译错误单独展示，不能把导入成功等同于工程可用。

ZIP：下载 .part → 哈希验证 → 暂存目录解压 → 检查路径穿越/绝对路径/符号链接与大小 → 按确定布局逐项应用 → Refresh/核验。保留 GUID/.meta，覆盖前检测已有文件；多文件应用不是原子操作，逐项日志支持识别部分完成。

执行器不得依赖正在安装的包、SharpZipLib 或 MTP 业务 API 才能恢复。下载/网络不在主线程同步等待；Unity API 回到主线程执行。忙碌/Play Mode/模态窗口时排队并显示等待。

## 7. 中断、超时、取消

建议起始阈值（均可配置，实测后调整）：

- 轮询/心跳约 5 秒。连续 60–90 秒无联系显示“等待 Unity 连接”，保留步骤与授权归属，不报安装失败。
- 文件下载/HTTP 可有限退避重试；下载重试复用制品哈希。与已经启动的 UPM/导入重试分开。
- 10 分钟无实际进展进入诊断核对；30 分钟总时长触发人工检查提示。有心跳不等于有进度；时间阈值不证明操作已停止。
- 等待用户不计入安装超时；关闭网页不等于取消。长时间等待可提示，不能默认同意导入。

服务重启：从 DB 恢复 Job，保留当前步，等 Unity 重传并核对；不从第一步重发。

Unity 域重载：从本地日志进入核验，不依赖旧 Task/AddRequest。未发生重载则走正常完成路径。

Unity 崩溃/重启：新会话恢复握手；文件完整则核验完成，部分应用则进入修复/重试决策，缺少证据则待人工核对。

安装成功但回执丢失：Unity 本地保存成功结果，重复发送；服务幂等提交。首版断网完成当前步后等待服务确认，不自行取下一步。

超时后恢复：先获取旧操作结果与当前状态；只有确定旧操作不再运行、步骤未达成且重试前置条件成立时才创建新 attempt。不能通过增加 timeout 后重新发 Add/Import 来“恢复”。

暂停/取消：停止后续下发。已开始的不可取消导入/UPM 操作允许收尾并核验，显示“取消请求已记录，等待当前步骤结束”；取消不自动卸载已安装包。仅对尚未产生修改的下载/排队阶段即时取消。

不承诺全工程自动回滚。对受控文件覆盖可备份并条件恢复；插件执行的外部操作与任意导入器副作用不具备通用逆操作。

## 8. 插件标签页与删除

同一标签页提供仓库可用版本及选中工程的安装状态；显示六项简要信息、已安装构建、导入路径、被哪些包引用、导入/删除操作。遗留插件只有可信旧导入记录或重新验证后才标记为可管理；无法识别的旧目录不自动认领。

按“导入根目录”组织展示与删除预览，但默认不能对记录的根执行递归删除：Assets/Plugins 等可能被多个插件或用户文件共用。

实际删除依据每个文件的归属记录、GUID/哈希与引用关系；共享文件仍有引用则保留，已修改文件提示并默认保留，仅清理空目录及对应 .meta。确认根目录完全独占且没有额外文件时才可整根删除。保护 Assets 根、Packages、ProjectSettings 与 Bridge 所在目录。删除也作为持久化单步骤，支持部分删除恢复与结果核验。

插件升级要处理旧版本残留文件，不能只把新压缩包覆盖上去。计划先计算旧/新文件差异与修改冲突；被覆盖的用户/其他插件文件需要明确处理，首版建议阻止无法判断的覆盖。

## 9. 进度窗口

按实际拓扑顺序列出每一个安装与导入步骤：包/插件名、目标版本、阶段、耗时、结果。插件作为包下的子项，但保留独立 step_id；共享插件标注复用。

转圈只用于正在执行/核验且有合理存活证据的步骤；失联显示等待连接及最后上报时间，等待选择显示导入/跳过/暂停按钮。步骤成功、已满足、已跳过、失败分别显示，不能将跳过画为安装成功。

总体显示“已完成 X / Y 步，跳过 Z 步”，或明确标注按步骤计算的进度。UPM 不提供的字节进度不虚构。可选步骤从计划预览时列出，决定跳过后标为跳过，避免分母不断跳变。

页面状态从 DB 重建，刷新、换设备、关闭后重开都能继续；用户选择绑定 job/step/状态版本，重复点击幂等，过期页面操作被拒绝。提供当前阶段、最后联系时间、失败原因和“重新核对”入口。

## 10. 分阶段实施与验收

### 阶段 0：代表性验证与协议定稿

选取纯 UPM、UPM + 可选 unitypackage、UPM + 必需插件、ZIP、共享目录/文件、带自定义导入脚本的实际样本；明确支持的 Unity 版本与 ZIP 布局。验证域重载前后回调顺序和编译失败时 Bridge 可用性，固定成功证据与不支持范围。

产出：小型验证结论、协议/schema、插件样本清单。先证明执行器可恢复，再扩大批量功能。

### 阶段 1：插件仓库与映射

建立 external/magictavern 存储规范、六字段 JSON、技术 manifest、精确版本映射与验证/索引命令。扫描已有包生成迁移预览；插件标签页先只读。

验收：同版本不同内部构建可区分；缺失/损坏制品不上架；能准确查出指定包版本的插件。

### 阶段 2：单条 UPM 可靠闭环

建立 Job/Step/Attempt/Event、工程串行锁、Unity 本地日志与回执重试；接通一个包安装与网页步骤状态。

验收：域重载、服务重启、回执丢失、重复下发、Unity 重启、超时迟到结果均不导致盲目重复安装或错误成功。

### 阶段 3：单条插件导入与记录

先 unitypackage，再已确定布局的 ZIP；制品下载校验、导入前文件基线、回调/重载核验、共享归属记录与网页可选插件决策。

验收：成功、取消、失败、部分导入、编译错误、重载丢回调、用户文件冲突均有明确结果。

### 阶段 4：完整计划与进度窗口

依赖求解、版本/commit 固定、拓扑排序、必需插件顺序、可选插件选择、计划预览与最终全图核验；页面恢复与重复操作保护。

验收：菱形依赖去重、循环/版本冲突阻止、安装期间工程变化触发重新核对、共享插件不重复导入、跳过语义正确。

### 阶段 5：插件管理与删除、故障验收

提供导入/删除管理、文件差异与保留提示、条件备份恢复；覆盖断网、睡眠、切后台、编辑器卡住、服务重启、文件损坏及缺少日志等故障。

验收：共享/修改过的文件不被静默删除；已执行步骤不会因刷新或重启重做；不能恢复时给出可操作的阻塞原因。首个发布仅承诺已验证的 Unity 版本与制品布局。

## 11. 建议讨论确认的默认选择

1. JSON 为插件展示元数据与包映射的首期源，DB 保存运行状态/索引；制品构建不可变。
2. 保留单步骤执行，但允许必需插件提前；不能安全单步安装的包组合先调整打包。
3. ZIP 逐个确认布局，不统一假定解压至 Assets/Plugins，也不长期写入 PackageCache。
4. 超时进入等待核对，禁止自动重发未知状态的导入。
5. 删除以文件归属为准，根目录用于组织展示；不承诺任意根递归删除。
6. 先在实际使用的一个 Unity 版本完成故障验证，再扩展支持矩阵。
