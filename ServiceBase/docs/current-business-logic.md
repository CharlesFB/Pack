# ServiceBase 当前业务逻辑

整理日期：2026-10-08。范围：本仓库的 Django 服务端、网页工作台、`unity/` Bridge 与独立执行器，以及仓库和部署管理命令。当前源码执行器版本为 **v10**。

本文描述代码已实现的业务能力，不把历史设计稿中的待办视为已完成，也不表示当前部署环境或每个业务工程已经通过实机验收。本次为代码和文档核对，未实际安装、更新、卸载插件或运行 Unity 验收。

## 1. 产品定位与业务对象

ServiceBase 是通过网页集中管理 Unity 工程、UPM 包和 Assets 插件的工作台。Unity 主动连接服务器，服务器保存目录、预览和任务，Unity 执行本机工程修改并回传结果。

- **工程**：具体设备上的 Unity 工程，拥有稳定工程标识和每次编辑器启动的会话标识。
- **UPM 包**：由 Unity Package Manager 管理的包；可按明确 Registry 版本或固定 Git commit 执行操作。
- **Assets 本地包**：通过 Assets 内的 `package.json` 独立识别；参与展示和依赖保护，但不由 UPM 入口移动或删除。
- **插件**：仓库中的 `unitypackage` 或 ZIP 制品，以插件 ID、版本和构建哈希区分；导入 Assets 后保存独立记录。
- **安装计划**：根据工程当前状态生成的固定操作序列，包含包、插件、清理和最终核对步骤。
- **任务、步骤、尝试**：分别记录一次业务操作、操作中的单项工作、该步骤的执行或人工重试。

## 2. 账号、设备与访问权限

1. 支持网页登录与退出。管理员可查看所有账号下的工程；普通成员只能访问本人账号下、当前浏览器会话绑定设备的工程。
2. 普通成员通过设备 Token 绑定或解除当前浏览器的设备。仅登录账号不自动获得工程列表；退出后需重新绑定。
3. 同一设备可连接多个工程；不同设备应使用不同 Token。设备身份由凭据决定，不是硬件认证。
4. 支持命令行创建和撤销设备凭据；服务端保存设备 Token 的摘要，撤销后拒绝该设备访问。
5. 网页账号密码、设备 Token、服务器 GitLab Token 分别用于网页登录、Unity 通信和仓库读取。
6. 本地开发模式只接受回环地址；匿名本地请求只访问无账号和设备归属的本地工程。

代码依据：`dashboard/auth.py`、`dashboard/admin_settings.py`、`dashboard/management/commands/create_bridge_token.py`、`revoke_bridge_token.py`。

## 3. 工程接入、在线状态与调试

1. 在 Unity 放入完整 Bridge 和 UpmExecutor 脚本，通过菜单配置服务器地址、设备 Token，并启动、停止或重新连接。
2. 连接设置保存于本机 EditorPrefs，环境变量可覆盖；同一系统用户的多个工程共享设置。存在未确认任务时，设置页限制切换服务器。
3. Unity 主动注册和轮询服务器，无需开放用户电脑的入站端口。
4. 工程注册记录名称、路径、设备名、Unity 版本、进程和当前会话。既有工程不能由其他凭据静默接管。
5. 网页支持按工程名搜索、分页和选择工程，并展示在线、离线和最后联系时间。
6. 在线状态由心跳判定；关闭 Unity 或连接中断后转为离线，历史工程记录保留。
7. “移除工程”仅隐藏当前编辑器会话，不删除工程文件和历史数据。支持恢复；新编辑器会话可重新出现。
8. 网页可发送字符串调试消息，Unity Console 输出消息并回传反馈；可以查询消息任务的完成或过期状态。这不是任意代码执行入口。
9. 旧本机 Bridge 协议保留兼容处理，远端生产通信要求新版主动连接协议。

代码依据：`dashboard/bridge.py`、`dashboard/views.py`、`unity/BridgeSettings.cs`、`unity/BridgePullClient.cs`。

## 4. 共享包目录与工程包展示

### 4.1 目录维护

- 管理员配置 GitLab HTTPS 地址、目录分支、访问 Token、工程 ID 黑名单与 Debug 开关。Token 留空保留原值，页面不回显。
- 管理员可以主动同步共享包目录；同步失败保留上次缓存。
- 目录缓存按来源地址、凭据和分支隔离，合并包索引与各 Tag 元数据。
- 黑名单隐藏未安装的指定工程包；已安装包保留，依赖树保持完整。Debug 开关可显示被隐藏目录项。

### 4.2 浏览与工程状态

- 展示共享目录与当前工程安装状态，区分根包、依赖包、未安装包及 Assets 本地包。
- 包列表按已安装根包、已安装依赖、未安装分组，再按展示名排序；支持包筛选和详情查看。
- 包详情提供版本、Tag、说明、Unity 要求等元数据，以及依赖和更新日志；缺少元数据时明确提示。
- 切换 Tag 只改变预览，不直接安装或更新。
- 工程依赖树支持展开、收起，保留共享依赖、循环和缺失节点提示。
- 工程主视图聚焦 MT Git 包并保留 MT 本地包提示；Registry 和 Unity 内置包仍参与底层解析及保护，不因界面过滤被忽略。
- 根包与依赖身份结合实际依赖图和服务安装记录计算，不只依据 Unity 的“直接依赖”字段；共享依赖可在多个父节点下展示。
- 安装时固定 commit；展示时仅在有准确历史证据时还原发布 Tag，无法唯一确认则显示 commit。

### 4.3 当前状态来源

- 独立执行器读取 UPM 注册包、manifest/lock 相关状态、Registry 配置及 Assets 包元数据，并上传快照。
- 最新 Bridge 已停用自动 MTP 读取；普通刷新不主动扫描或迁移旧 MTP 记录。独立包状态主要由执行器空闲采样更新。
- 离线、旧会话、过期或扫描异常状态不能作为新修改计划的有效基线；包基线新鲜度限制为 120 秒。
- 同名 Assets 包目录全部保留并标注冲突；发现 `package.json` 只证明识别到了包元数据，不证明全部文件完整。

代码依据：`dashboard/catalog.py`、`dashboard/package_presentation.py`、`dashboard/package_state.py`、`dashboard/static/dashboard/app.js`、`unity/UpmExecutor/ProjectPackageState.cs`、`AssetsPackages.cs`。

## 5. 包安装与依赖解析

标准流程：**选择工程与发布 Tag → 预览依赖 → 选择附带插件及 ZIP 目录 → 检查冲突和执行顺序 → 确认 → Unity 串行执行 → 最终核对。**

1. 读取目标版本真实 `package.json`，把 Tag 解析为固定 commit，支持 Git 仓库子目录。
2. 合并标准依赖、`dependenciesGit`、其他根包及 Assets 本地包约束，校验 Unity 要求、依赖循环和来源冲突。
3. 对配置 GitLab 上同仓库、同子目录的 MT 依赖，依据明确版本号统一到满足当前需求的较高版本；不自动追逐仓库最新版本。
4. 用户明确选择根包时允许降级，但必须满足其他根包约束。同名不同仓库、同最高版本但不同 commit 等情况不任意合并。
5. 插件映射采用精确包名和 commit，不借用其他版本的映射；缺失或不一致时要求先整理元数据。
6. 预览区分新增、变更和已满足包，展示附带插件、冲突、清理项及保留原因。预览本身不修改 Unity 工程。
7. 插件逐项选择；同一构建、同一目标目录去重。不同版本、文件路径重叠或 GUID 冲突会提示；预览警告允许继续，执行前的硬性文件保护仍可阻止实际写入。
8. 依赖先于依赖它的包执行；选中的插件先于所属包执行；未选插件和重复项保存为跳过步骤。
9. 确认时再次检查预览摘要、插件选择、工程会话、状态指纹、执行器能力和工程锁。预览确认有效期为一小时；选择变化后需重新检查。
10. Registry 安装要求明确版本；Git 执行目标使用不含凭据的 HTTPS 地址和完整 commit。元数据解析兼容经校验的同源 SSH 地址，但不会把服务端 GitLab Token 下发给 Unity。
11. Unity 机器必须自行具备 Git 访问权限。Registry 来源受服务器允许列表限制；当前不支持额外私有 Registry 认证配置。
12. 原始单包安装 API 仍支持固定 Registry/Git 目标；网页已统一使用包或插件详情入口，不再提供直接填写标识的调试表单。

代码依据：`dashboard/plan_resolver.py`、`dashboard/installation_plans.py`、`dashboard/installations.py`、`dashboard/static/dashboard/installation-plan.mjs`。

## 6. 包更新、卸载与依赖清理

### 6.1 包更新

- 已安装包选新发布 Tag 后预览更新，重新计算新依赖图、变更包、旧依赖和插件。
- 先安装新图，再清理可确认已无引用的旧服务依赖。
- 附带插件可选择新导入，或选择现有插件记录做替换更新。
- 不再关联的旧插件可单独勾选清理，默认保留；先完成包操作，再执行清理。

### 6.2 包卸载

- 从已安装根包预览卸载，按实际安装身份生成固定目标，而非使用正在浏览的其他 Tag。
- 根包仍被其他包引用时拒绝卸载；保留其他根包需要的共享依赖。
- 自动清理只覆盖能证明由服务添加、版本和来源仍匹配、未被用户提升为根包的无引用依赖。
- 原有依赖、归属不明确或检测到外部改版的依赖保留。间接依赖交给 UPM 解析，最终检查其应有状态。
- MTP 自身、本地包和嵌入包不能由此入口删除；Assets 包声明的依赖参与卸载保护。
- Unity 在操作前再次检查引用和包身份，备份 manifest/lock，保存执行意图后调用 Remove；恢复时核对结果，不重复卸载。

代码依据：`dashboard/package_maintenance.py`、`dashboard/plugin_updates.py`、`unity/UpmExecutor/PackageRemover.cs`。

## 7. 插件仓库浏览与内容预览

1. 不连接 Unity 也能浏览仓库；实际导入、更新或删除需要选择可用工程。
2. 支持分类、名称/ID 搜索、分页、版本和构建切换。
3. 查看格式、说明、Unity 要求、制品大小、资源数量、哈希、当前/历史构建、来源及引用它的包版本。
4. 展示制品缺失、大小不匹配、元数据异常、路径和导入限制，不将所有可见构建视为可导入。
5. 支持按目录浏览指定构建的归档资源索引、分页以及显示/隐藏 `.meta`；无需实际导入或展开归档到工程。
6. 选择工程后显示该工程的导入记录、导入目录、操作结果与管理入口。

代码依据：`dashboard/plugin_api.py`、`dashboard/plugin_contents.py`、`dashboard/static/dashboard/plugins.js`、`plugin-contents.mjs`。

## 8. 插件导入：unitypackage 与 ZIP

### 8.1 共用流程

- 锁定精确构建，服务端准备固定制品和资源清单；Unity 通过工程、设备和会话鉴权下载。
- 下载与暂存仍核验大小、SHA-256、清单及路径；拒绝路径越界、链接、类型冲突和不支持的归档内容。
- 写入前保存归档路径、原有文件信息及不可覆盖的执行意图；导入结果和归档清单保存到 `.servicebase/`。
- 初次导入不能静默覆盖内容不同且不属于该构建的已有文件；同构建重复导入保留首次原有文件信息。
- `unitypackage` 使用 Unity 导入器；ZIP 按确认目录展开并刷新资源。

### 8.2 ZIP 目录选择

- 在网页按层浏览目标工程现有 Assets 目录，也可以输入路径读取；目录由 Unity 执行器返回，服务器不直接访问用户电脑磁盘。
- 只允许现存 Assets 或其子目录，不通过该入口创建目录，不允许 Packages、ProjectSettings、其他工程或符号链接目录。
- 确认前取消仅关闭选择器；确认后目录随任务固定，重启恢复及允许的重试沿用原目录。
- 保留 ZIP 全部原始层级，不自动去除最外层。例如 ZIP 内为 `Assets/Foo`，目标选 Assets 时实际为 `Assets/Assets/Foo`。
- ZIP 可为缺少的 meta 生成稳定 GUID；已有相同内容资源按既有规则保留工程 meta。

### 8.3 v10 完成与失败规则

- 当前按导入回调和持久执行日志判定完成，**不再在导入后逐文件扫描内容、数量、meta 和 GUID 来保证完整**。
- 插件自行改写 DLL、删除旧文件或生成资源，不单独导致导入失败；额外生成文件不自动进入归档归属清单。
- 状态页“已保存导入记录”表示记录存在，不表示插件全部资源完整，也不表示工程编译通过。
- 安装计划中的插件导入失败、取消、编译报错或未确认完成，可记录原因后跳过，并从最终插件核对目标移除，继续后续包步骤。
- 跳过不回滚已导入的部分文件；保留记录供查看和后续删除。网络断开时必须恢复同步后才能继续服务队列。
- 单独插件替换更新仍采用独立的严格备份和替换规则，不能套用普通导入的宽松完成判定。

代码依据：`dashboard/plugin_delivery.py`、`dashboard/plugin_installations.py`、`unity/UpmExecutor/PluginImporter.cs`、`PluginInventory.cs`；规则说明见 [v10 插件执行](plugin-execution-v10.md)。

## 9. 插件更新与删除

### 9.1 替换更新

- 对同插件选择新构建和旧导入记录，预览新增、替换、清理、保留文件及 GUID 变化。
- ZIP 更新沿用原目录；无法保留原目录的跨格式变化不自动迁移。
- 完整暂存并检查资源归属、其他插件共享引用、实际文件状态后，备份待替换和清理内容。
- 替换文件要求由旧插件独占创建且未被修改；原有文件、共享文件或用户修改会阻止相关覆盖。
- 新版本不再使用的资源，只清理可安全处理的旧文件；保留用户修改、原有、共享及额外文件，仅清理空目录。
- 新记录、旧记录归档与更新回执配套保存，服务端取得所需证据后才确认成功。
- 精确包映射证明插件仍被包使用时，独立替换或删除受阻，需要通过相应包计划处理。

### 9.2 删除：当前 v10 语义

- 以精确导入记录及其摘要确定清理范围，不按插件目录名猜测版本，不递归删除整个根目录。
- 保留其他插件记录、已手动迁移的旧插件记录和其他 Assets 本地包占用的路径；归属记录损坏时拒绝预检。
- **归档清单内未共享的文件会移到本机 trash 备份，即使文件后来被修改，或在首次导入前就已存在。** 这与历史 v6–v9 文档中的保留规则不同。
- 资源不存在时记录为无需删除；路径类型改变时保留。对应 meta 一并处理，文件夹只在空目录时清理。
- 清单之外的生成文件、额外用户文件不自动删除；因此删除成功不代表磁盘上的全部相关资源已消失。
- 保留原记录和处理回执。部分写入异常需人工处理后核对，不反复执行删除；没有一键撤销和自动清空备份功能。

代码依据：`dashboard/plugin_updates.py`、`dashboard/plugin_inventory.py`、`unity/UpmExecutor/PluginUpdater.cs`、`PluginRemover.cs`。

## 10. 任务编排、进度与恢复

1. 每个工程同一时间只能有一个活动修改任务；不同工程的任务分别管理。
2. 请求 UUID、步骤尝试和回执序号用于幂等处理。重复提交不应重复创建同一任务；相同标识不能更改目标或回执内容。
3. 网页展示最近 10 条未隐藏任务、逐步结果、进度、失败原因、等待连接、需要核对和人工重试记录。
4. 任务和进度保存在服务端数据库；关网页不会取消任务，重新打开可继续查看。
5. 安装计划支持暂停、恢复和取消后续步骤。已派发操作不会被直接中断；取消不回滚已完成操作。
6. 完成回执接受后，等待 Unity 确认并归档上一项，再派发下一项，避免丢确认造成重复执行。
7. 每步操作前检查工程状态指纹；操作成功保存新的指纹；最终核对目标包、受保护依赖、manifest/lock 和注册状态等。
8. 域重载、编辑器或服务重启后，依据持久日志、意图和回执恢复；已经开始的修改原则上核对结果，不重新 Add、导入或删除。
9. “重新核对”是检查既有操作结果，不等于重装。仅满足明确失败类型及当前任务状态条件时允许填写原因新建 Attempt。
10. v10 普通插件导入失败可跳过；UPM 安装或最终包图核对的明确失败会结束计划，跳过尚未执行步骤并释放服务队列。更新、删除部分写入或无法确认的结果仍可能占锁，不能把断线或页面超时当成失败终态。
11. 工程持续编译、资源刷新、播放切换、执行器无法加载、日志损坏等会影响继续执行；工程已有编译错误且关闭 Unity 后，需先恢复编译才能重新加载执行器源码。
12. 已结束任务支持从网页历史删除，实际为软隐藏；步骤、回执和依赖归属证据保留。活动或待核对任务不能删除，隐藏记录不能从旧页面重试。

代码依据：`dashboard/models.py`、`dashboard/installations.py`、`unity/UpmExecutor/UpmExecutor.cs`、`InstallJournal.cs`、`dashboard/static/dashboard/installations.js`。

## 11. 旧 MTP 记录的主动迁移

标准流程：**打开迁移面板 → 主动读取旧记录并预览 → 逐项勾选 → 确认 → 保存 ServiceBase 历史归档。**

- 打开网页、启动 Unity、连接或普通刷新不会触发旧记录扫描；默认全部不勾选。
- 支持读取已知结构的根包、本地包、依赖历史及 `plugin-assets.json` 插件路径记录。
- 只读取白名单字段和摘要，不调用 MTP 业务 API，不迁移 Token、旧 URL 和编译宏等内容。
- 预览绑定会话，30 分钟后失效；确认时重新检查源摘要、资源状态和是否已迁移。
- 仅保存选中项的历史来源和当前基线，不改写原 MTP 记录、不搬动 Assets 文件。
- 已迁移记录可显示与基线一致、修改或异常情况；包当前安装状态仍来自独立扫描。
- 旧插件记录不能证明精确构建或首次文件归属，因此不会自动成为普通插件的可更新、可删除记录；迁移路径参与新插件操作的共享保护。
- 迁移使用统一工程锁和日志，重复请求或重启复用归档；单次最多 500 条记录、20,000 项资源，累计最多 500 条记录。
- 该功能是选择性历史归档，**尚不是可重复执行的 MTP → ServiceBase 双方状态同步**。

代码依据：`dashboard/legacy_migration.py`、`unity/UpmExecutor/LegacyMigration.cs`、`dashboard/static/dashboard/legacy-migration.js`。

## 12. 插件仓库维护与部署支持

### 12.1 已有命令行仓库能力

- 从本地工程导入插件制品，校验仓库索引和制品一致性。
- 扫描 GitLab 包目录，导入插件及精确包映射；支持按指定工程和 Tag 补齐历史映射。
- 按指定清单同步外部插件来源，保存来源信息、归档清单及内容哈希。
- 支持仓库目录布局整理；旧 ZIP 布局配置命令已不再决定新任务的导入目录。
- 这些是管理员命令行能力；目前没有完整网页上传、发布、元数据编辑和映射管理流程。

### 12.2 部署与运维能力

- 提供本地开发、通用生产部署、Mac 常驻服务及 Docker 配临时 HTTPS 隧道的部署方案。
- Quick 工具支持初始化、启动、停止、状态查询、同步变化后的隧道域名、更新服务及创建成员设备凭据。
- 更新流程支持数据库备份、迁移、静态资源更新和部署检查，保留原有启停状态。
- 提供设备撤销、过期 Bridge 任务清理及安装部署自检命令。
- 服务数据库、固定制品缓存与 Unity 工程 `.servicebase/` 中的日志和备份共同支撑恢复；清理 Library 不能代替管理这些运行数据。

代码依据：`dashboard/management/commands/`、`dashboard/plugin_repository.py`、`plugin_catalog_sync.py`、`plugin_external_sync.py`、`deploy/quick/quickctl.py`。

## 13. 当前明确限制

1. **MTP 严格共存尚未实现。** 检测到已知 MTP 包、程序集或恢复记录时，阻止新资源安装、更新、卸载和插件修改；只读能力及允许的历史记录迁移不等于开放资源操作。
2. **没有整套事务回滚。** 多步骤或文件写入失败可能留下部分已完成内容；取消和跳过不撤销这些内容，备份恢复仍需人工处理。
3. **不是通用插件兼容认证器。** 导入记录存在不证明插件文件完整、商业插件可用或工程编译无误；Unity 版本元数据缺失时也无法据此保证兼容。
4. **未接管所有旧资源。** 手动导入、MTP 旧插件和缺少准确记录的资源不能靠目录名自动认领。
5. **Assets 本地包只识别和保护。** 当前不通过包管理入口自动转换、移动或删除这些目录。
6. **并非任意 Git/Registry 解析器。** 受配置来源、明确版本、完整 commit 和凭据条件限制，模糊版本和额外私有 Registry 认证不在现有支持范围。
7. **尚无完整仓库发布后台或新版打包器闭环。** 已有导入、同步和验证命令，上传发布、在线编辑映射等仍是后续工作。
8. **没有自动定期 MTP 同步。** 当前保留用户主动选择的历史归档，不自动同步或修复 MTP 数据。

## 14. 已形成的主要业务闭环

- 管理员准备账号和设备 → 成员连接 Unity → 网页绑定设备 → 查看工程与调试消息。
- 同步共享目录 → 查看工程包与依赖 → 预览安装/更新 → 选择插件 → 确认队列 → 查看结果。
- 选择已安装根包 → 预览卸载及共享依赖保护 → 确认可选清理 → 执行与核对。
- 浏览插件仓库与资源索引 → 选构建及目标工程 → 导入 → 保存本机与服务端记录。
- 选已有插件记录 → 预览新构建差异并更新，或按归档范围删除 → 查看保留项及备份结果。
- 发生断线或重启 → 恢复既有任务 → 核对结果或按允许条件人工重试 → 归档历史。
- 主动读取旧 MTP 历史 → 逐项确认 → 保存独立基线 → 展示历史与保护共享路径。

以上闭环均受各节的权限、执行器版本、MTP 边界和状态新鲜度约束。
