# 第 9 步：包卸载与插件更新

2026-09-22。独立执行器 **v8**，服务端迁移 **0012_pluginupdatereceipt**。统一编号见 [开发顺序](development-order.md)。

## 操作入口

- 工程包详情：选择发布 Tag，点击「预览更新」；已安装根包提供「卸载」。预览列出新增/变更包、将卸载的包、保留的旧依赖及原因。
- 包附带插件：可选择另行导入，或指定同一插件的旧导入记录进行更新。ZIP 更新沿用原目录；新导入仍由网页选择目录。无法沿用原目录的跨格式更新不自动迁移，需另行导入。
- 插件详情：选择新版本，对工程中同插件的旧构建点击「预览更新到所选版本」。文件差异列出新增、替换、待清理、复用/保留以及 GUID 变化。
- 包更新或卸载后，不再关联的旧插件提供可选清理项，默认不勾选。先完成包操作，再清理插件。已通过更新替换的旧记录不再重复删除。
- 检查执行顺序后确认；每步独立显示进度，可暂停/取消尚未派发的后续步骤。操作记录在服务端持久化，关闭网页不停止执行。

## UPM 卸载与旧依赖清理

`package_maintenance.py` 从已成功执行的服务任务重建依赖归属：仅清理可证明由服务添加、未被用户显式提升为根包、当前版本和来源仍匹配的直接依赖。既有根包、来源不明确的项及检测到外部改版的项保留。新计划保存包基线，外部更改后再由服务更新不会重新取得自动删除权限。历史任务缺少基线时只能依据已有记录判断；无法检测用户曾修改又恢复为完全相同状态的行为。

更新先安装新依赖图，后清理旧图中的无引用服务依赖；卸载按根包到依赖的顺序执行。保留其他根包可达的共享依赖。只有间接依赖的项交给 UPM 自动解析，最终检查它们确实消失。包仍被其他包引用时，根包卸载被拒绝。本地包、嵌入包和 MTP 自身不由此入口删除。

`PackageRemover.cs` 再次核对版本、来源和当前引用，备份 manifest/lock，保存意图后仅调用一次 `Client.Remove`。重载后核对 manifest、lock、注册包及编译状态。清单变化导致的预览失效、操作结果未知和超时不会被当作成功。

## 插件文件更新

`PluginUpdater.cs` 使用与初次导入相同的下载鉴权、大小/哈希和安全路径校验。先完整暂存制品、生成文件操作表、检查本地旧归属、其他插件共享引用及实际文件，然后备份全部待替换/清理内容。

- 待替换文件必须由旧插件独占创建，且当前内容与原记录相符；有用户修改、原有文件或其他插件仍引用时，预检停止。
- 新版本不再包含的文件，仅清理独占且未改动的文件；用户修改、原有、共享文件和额外目录内容保留。仅删除空目录。
- ZIP 自动生成的 `.meta` 延续原 GUID 和导入设置。明确随制品提供的 `.meta` 按新版本核验；GUID 变化在网页提示。文件改路径时，只有可安全移出的旧文件才允许转移其 GUID；目录类型和大小写迁移需要先处理。
- 更新后保存新归属，归档旧归属，并分别提交新文件回执与旧文件处理回执。服务端两份证据齐备后才接受成功，插件页显示保留文件摘要。
- 更新 unitypackage 时使用服务器已校验的资源清单和暂存文件批量应用，在 `StartAssetEditing` 范围内替换，结束后刷新；初次导入仍使用原有导入器。依赖交互导入窗口或自定义导入流程的插件需另行验证。

服务端按精确 package commit → plugin build 映射保护仍被包使用的插件。有关联包引用时，独立替换/删除被阻止，需随包计划处理。仅已有精确映射能够证明这种引用；未登记的脚本引用仍通过编译检查发现。Unity 逐文件保护不依赖此映射。

## 中断、失败与备份

- 每个步骤保存不可变目标、Attempt、操作意图和回执。派发后的未知结果只核对，不重新调用 Remove 或重新写入插件文件。
- 明确预检失败、明确 UPM 请求失败允许填写原因建立新的 Attempt；部分写入、编译失败、核验证据不足或未知结果保持工程锁，需修复后「重新核对」。若 UPM 失败时已改变清单，原计划基线不匹配时应取消后续步骤并重新预览。
- 插件写入不是文件系统事务。崩溃可留下部分新文件；备份和日志保留，不自动覆盖用户后续修改，也不自动回滚整个计划。
- 插件回执确认丢失时按相同 digest 重传；服务端保存回执与任务进度，编辑器重启或服务缓存清空不会重新更新。
- 单插件删除在 v8 下也绑定独立工程包基线，防止排队后包状态变化仍继续删除。

本地路径（工程根目录下，不在 Assets 内）：

- `.servicebase/upm/backups/<attempt>/manifest.json`、`packages-lock.json`：每次卸载前清单备份。
- `.servicebase/plugins/updates/<attempt>/backup/Assets/...`：更新前被替换/移出文件及 `.meta`。
- `.servicebase/plugins/updates/<attempt>/original-record.json`：更新前归属记录。
- `.servicebase/plugins/superseded/<attempt>.json`：更新成功后旧归属归档。
- `.servicebase/upm/active.json`、`history/` 和意图标记：操作与恢复日志。
- 原有插件删除备份仍位于 `.servicebase/plugins/trash/`。

恢复时先保留完整日志/备份，并检查当前文件；不要直接删除意图标记、锁或活动日志来强制重跑。没有自动回滚或一键恢复按钮。手动修复到预期结果后可只读核对并继续；无法达到预期时保持可见阻塞状态。

## 代码与部署

- `dashboard/package_maintenance.py`：服务依赖归属、删除顺序、保护集合。
- `dashboard/plugin_updates.py`：更新绑定、差异、归属校验、包引用保护及旧插件清理候选。
- `dashboard/installation_plans.py`：不可变预览与更新/卸载步骤组装。
- `POST /api/bridge/plugins/update-receipt/`：鉴权、工程/会话/Attempt 绑定的不可变更新结果回执。
- `unity/UpmExecutor/PackageRemover.cs`、`PluginUpdater.cs`：独立单条执行器；最终核验扩展了包缺失与旧记录移除检查。

服务端先备份数据库、应用 0012、更新静态资源；Unity 整体替换 `UpmExecutor/` 并保留已有 `.meta`。v7 可继续执行原有安装计划；新卸载/更新计划要求 v8，旧执行器无法领取。

不接管 MTP 记录，不调用 MTP 业务。已识别 MTP 工程仍被 `MtpBoundary` 阻止新修改，严格共存与记录迁移留待后续。新旧包与插件需要能在逐步执行期间通过编译；跨版本 API 不兼容导致的中间编译错误会停止计划，尚不支持把多包变更作为一次原子编译事务。
